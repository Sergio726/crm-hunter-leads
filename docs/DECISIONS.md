# 🧠 DECISIONS — Registro de decisiones

> Decisiones de arquitectura/producto ya tomadas, con el porqué. Evita rediscutir lo resuelto. Formato: fecha · decisión · motivo.

| # | Fecha | Decisión | Motivo |
|---|---|---|---|
| D1 | 2026-07 | **Stack: React Native + Expo + Supabase** | Un código para Android/iOS; Supabase da auth Google + Postgres + RLS + API REST sin backend propio. Ver ARCHITECTURE §Alternativas. |
| D2 | 2026-07 | **Single-tenant por instalación** (sin capa de "organizaciones") | Cada cliente tiene su copia aislada. Simple. Multi-tenant se descartó por ahora (meterlo después es caro pero hoy no se necesita). |
| D3 | 2026-07 | **Multi-CRM vía n8n**, app/base agnósticas al CRM | Agregar un CRM = un flujo n8n, sin tocar la app. Credenciales de CRM viven en n8n. |
| D4 | 2026-07 | **No construir API propia** — usar la REST autogenerada de Supabase | La base ya expone REST documentada + RLS. La "API a documentar" es el contrato con n8n (contacto normalizado). |
| D5 | 2026-07 | **Equipo por invitación** (lista blanca de emails) | Solo entra gente autorizada; los no invitados quedan en rol `pending` sin acceso. |
| D6 | 2026-07 | **Backend en Supabase Cloud** (proyecto del cliente), self-hosted como respaldo | Consolidar en el ecosistema del cliente. Se pausó ROADMAP.APP para liberar cupo free. |
| D7 | 2026-07 | **Expo SDK 54** (bajado de 57) | El Expo Go del cliente soporta SDK 54. |
| D8 | 2026-07 | **Web admin aparte, mismo backend** | Móvil = día a día del vendedor; Web = administración pesada. Comparten Supabase y tipos. |
| D9 | 2026-07 | **Secreto n8n↔Supabase viaja en el header `x-crm-lite-webhook-secret`**, no en el body | n8n no permite leer credenciales en expresiones (`$credentials` falla). Los nodos HTTP usan Header Auth nativa y los RPC leen `request.headers` (fallback `p_secret` para pruebas manuales). Un solo secreto para ambas direcciones. |
| D10 | 2026-07 | **`push_to_crm` solo empuja registros "dirty"** (`crm_synced_at` null en UPDATE) | El write-back de n8n actualiza la fila y sin este guard re-disparaba el push en loop infinito contra GHL. `mark_crm_dirty` repone el estado dirty cuando cambian datos de contacto o tags. |
| D11 | 2026-07-17 | **El 2º teléfono/email del cliente (`phone_2`/`email_2`, CONT-1) NO se sincroniza a GHL** — vive solo en CRM Lite | Decisión del usuario: el contacto secundario es para uso interno del vendedor, no hace falta enviarlo al CRM externo. Evita mapear `additionalEmails`/custom fields de GHL (soporte no nativo para 2º teléfono) y mantiene el contrato normalizado simple. Cierra CONT-1: la UI (alta + edición, app y web) ya guarda y muestra ambos campos. |
| D12 | 2026-08-13 | **Pausa de sync GHL vía flag `app_settings.crm_sync_enabled`** (no vaciar URLs) | Un interruptor en Configuración detiene push, inbound, auto-import, retry y notificaciones sin perder `n8n_push_url`/`n8n_notify_url` ni credenciales. Al reactivar, el retry retoma dirty. Contactos GHL manual queda fuera a propósito. |
| D13 | 2026-08-13 | **Prospección: los leads generados NO se sincronizan a GHL** (origen `hunter`) | Pedido explícito del usuario para esta etapa. Se aprovecha que `push_to_crm()` sale temprano cuando `origin <> 'app'` (D10/0007): basta con un valor de origen nuevo, sin tocar el trigger. Si más adelante se quiere empujarlos, es cambiar una condición. Mismo criterio en el guard anti-spam de `notify_lead_assigned`: la promoción es un alta en lote, no notifica. |
| D14 | 2026-08-13 | **Los resultados de búsqueda NO se persisten; se guarda solo lo que el usuario selecciona** | Una búsqueda es exploratoria y devuelve ruido. Persistir todo ensuciaría la base y obligaría a limpiar después. El paso "migrar a Supabase" es explícito, y la promoción a `clients` es un segundo paso separado: un prospecto crudo no debería aparecer en la bandeja de un vendedor sin que alguien lo haya mirado. |
| D15 | 2026-08-13 | **El asistente de avatar es opcional: sin API key el módulo degrada a modo guiado** | La IA ayuda a definir el ICP, pero no puede ser un punto único de falla para generar leads. Buscar, guardar y promover funcionan igual con los filtros cargados a mano. Evita además que una key faltante rompa el deploy. |
| D16 | 2026-08-13 | **El asistente corre sobre OpenRouter, no contra un proveedor fijo** | Pedido del usuario. Una sola integración (API compatible con OpenAI) da acceso a modelos de todos los proveedores y permite cambiar de modelo sin tocar código. El modelo se elige en Configuración; vacío = `openrouter/auto`. Como no todos los modelos soportan tool calling igual, el agente también acepta la propuesta como bloque ` ```json `. |
| D18 | 2026-08-13 | **El enriquecimiento con Instagram (Apify) va después del guardado, y NO recalcula el score** | Dos decisiones en una. (a) *Después*: cada consulta a Apify consume crédito, así que solo se paga por los prospectos que el usuario ya decidió conservar — enriquecer durante la búsqueda multiplicaría el costo por todo el ruido que se descarta. (b) *Sin tocar el score*: si el score cambiara al enriquecer, un mismo número significaría cosas distintas según si el prospecto pasó o no por Apify, y dejaría de ser comparable. La señal nueva vive en `ig_activity` (activo / tibio / dormido según la última publicación), que ya es accionable por sí sola. |
| D17 | 2026-08-13 | **Las API keys se cargan desde Configuración y viven en `private.integration_secrets`, no en `app_settings`** | `app_settings` es legible por cualquier usuario autenticado: una API key ahí la puede leer un vendedor desde el navegador. Los permisos se separan por RPC: escribir y ver el estado (últimos 4 caracteres) requiere superadmin; **leer el valor está concedido solo a `service_role`**, así que el secreto solo lo obtiene el servidor. Costo: la web necesita `SUPABASE_SERVICE_ROLE_KEY` en su entorno — matiza la regla de "service_role nunca se materializa", que apuntaba al cliente móvil; acá vive en un route handler server-side y no entra al bundle. Queda el fallback por variables de entorno para quien prefiera no dársela. |
| D19 | 2026-08-14 | **Manual visual separado del repositorio de producto** | La identidad ST Labs + Turbo se mantiene en el repositorio hermano `crm-hunter-leads-brand`; `crm-hunter-leads` solo documenta cómo consultarlo. Así las exploraciones visuales y sus assets no interfieren con el código operativo hasta que una futura tarea de UI sea aprobada. |
